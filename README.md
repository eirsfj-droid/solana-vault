# Simple Vault — Практика Anchor (Неделя 8)

Учебный смарт-контракт на базе Anchor 0.31.1 (Solana), реализующий базовый каркас децентрализованного хранилища (Vault) и механизм персональных карточек пользователей.

## Архитектура и теория PDA (Program Derived Address)

### Что такое PDA?
**Program Derived Address (PDA)** — это детерминистически вычисляемый публичный ключ (адрес аккаунта), для которого **принципиально не существует соответствующего приватного ключа**. 

В обычной криптографии Solana ключевая пара генерируется на эллиптической кривой Ed25519. PDA намеренно вычисляются таким образом, чтобы точка лежала **вне эллиптической кривой (off-curve)**. 
- Вычисление адреса происходит с помощью функции:
  $$\text{PDA} = \text{find\_program\_address}([\text{seeds}], \text{program\_id})$$
- Функция перебирает специальный байт `bump` (от 255 вниз до 0), пока полученный хеш SHA-256 не окажется за пределами кривой Ed25519.
- Так как приватного ключа нет, ни один внешний пользователь или злоумышленник не может сгенерировать подпись от имени PDA.
- Единственный субъект, который может подписывать транзакции от имени PDA — это сам смарт-контракт (`program_id`), используя системный вызов `invoke_signed` (в Anchor обёрнутый в `CpiContext::new_with_signer`) с передачей исходных сидов и bump.

### Сиды хранилища (Vault Seeds)
```rust
seeds = [b"vault", token_mint.key().as_ref()]
```
- Префикс `b"vault"` задает пространство имен аккаунта состояния хранилища.
- `token_mint` гарантирует, что для каждого конкретного SPL-токена существует ровно одно детерминированное хранилище `VaultState`. Это исключает коллизии и дублирование состояния.

### Сиды карточки пользователя (User Card Seeds)
```rust
seeds = [b"user_card", vault_state.key().as_ref(), user.key().as_ref()]
```
- Префикс `b"user_card"` разделяет домен пользовательских карточек.
- `vault_state` привязывает карточку к конкретному пулу/хранилищу.
- `user` фиксирует владельца (публичный ключ кошелька).
- Благодаря такой структуре сидов один пользователь в одном хранилище может владеть **строго одной карточкой** (`UserCard`). Повторная попытка инициализации неизбежно завершается ошибкой рантайма Solana, так как аккаунт по данному адресу уже существует.

## Структура аккаунтов

### `initialize_vault`
Инициализирует глобальное состояние хранилища:

| Аккаунт | Seeds | Описание |
|---|---|---|
| `vault_state` | `[b"vault", token_mint]` | Хранит admin, token_mint, адреса vault_token_account и share_mint, bump |
| `vault_token_account` | `[b"vault_tokens", token_mint]` | Токен-аккаунт хранилища, владельцем (authority) которого является `vault_state` PDA |
| `share_mint` | `[b"share_mint", token_mint]` | Минт share-токенов (6 decimals), authority минта — `vault_state` PDA |

### `create_user_card`
Создает персональную карточку пользователя:

| Поле | Описание |
|---|---|
| `vault` | Публичный ключ хранилища `vault_state` |
| `owner` | Публичный ключ владельца карточки |
| `bump` | Сохраненный bump seed для быстрой валидации PDA |

## Тестирование

```bash
yarn test
```

Сценарий тестов 8-й недели:
1. `initialize_vault: vault создан` — проверка корректности полей состояния и привязанных PDA.
2. `create_user_card: у каждого пользователя своя карточка` — создание карточек для пользователей A и B.
3. `create_user_card: вторая карточка для того же пользователя — ошибка` — проверка защиты от повторного создания аккаунта по одинаковым сидам.
